# 1.1 パフォーマンスを学ぶために必要なこと

パフォーマンスとは、システムが「どれだけ速く」「どれだけ多く」仕事ができるかを表す指標。  
ただし、その裏には **CPU・メモリ・ストレージ・ネットワーク** という要素が密接に絡んでいる。

例として「料理店」を考えると分かりやすい：

| コンピュータ | 飲食店の例え |
|--------------|-------------|
| CPU | 調理人の数・腕前 |
| メモリ | 作業台の広さ |
| ストレージ | 食材庫・冷蔵庫 |
| ネットワーク | 仕入れの配送速度 |
| スループット | 1時間に何皿出せるか |
| レスポンス | 1皿が出るまでの時間 |

パフォーマンスを学ぶ上で重要なのは：

1. **全体構造を理解すること（CPU・メモリ・IOの関係）**  
2. **測定できること（ツールの使い方）**  
3. **データ構造・アルゴリズムを見る視点を持つこと**  
4. **アプリ・OS・ハードウェアがどう連動するかを理解すること**


# 1.2 アルゴリズムのメリット／デメリットと学習法

## 1.2.1 アルゴリズムとは

アルゴリズムとは「問題を解決するための手順」。  
つまり **レシピ**。

同じ料理でも、
- 手順が悪いと遅い  
- 手順が良いと速い  

これはプログラムも同じ。


## 1.2.2 アルゴリズムの根幹：計算量と空間計算量

アルゴリズムの性能を左右するのが **計算量**。

### ● 時間計算量（Time Complexity）
「処理時間がデータ量に応じてどれくらい変化するか」

例で整理：

| 計算量 | 例 | 日常の例え |
|-------|---|-----------|
| **O(1)** | 配列アクセス | 冷蔵庫のドアを開けて、飲み物1本取る |
| **O(n)** | 線形探索 | 本棚から該当の本を探す |
| **O(n log n)** | 多くのソート | 本棚を著者名順に並び替える |
| **O(n²)** | 二重ループ | 全員と1回ずつ握手する |

n が 1,000 を超えると、O(n²) は現実的に破綻する。

### ● 空間計算量（Space Complexity）
「メモリをどれだけ使うか」

例：
- バッファを大量に確保する = 作業台を大きく使う  
- 同時に保持するデータ量が大きいほどメモリを圧迫  


## 1.2.3 アルゴリズムを学ぶコツ

1. **図で理解する**  
   文章だけで理解しようとすると難しい。必ず図示する。

2. **実装する**  
   体で覚えるのが一番早い。

3. **ベンチマークを自分で取る**  
   「速さの違いを肌で感じる」ことが成長につながる。


# 1.3 アルゴリズムの実例とパフォーマンスの違い

## 1.3.1 身近なアルゴリズム

- エレベーターの停止順（スケジューリング）  
- Google検索（ハッシュ＋インデックス探索）  
- 時計のスヌーズ機能（時間管理）  
- Amazonのおすすめ（グラフ分析）  

すべてアルゴリズムで動いている。


## 1.3.2 パフォーマンスへの影響度合い

CPUの性能が2倍になっても **O(n²) のアルゴリズムはほぼ改善しない**。  
逆にアルゴリズム改善は **数百倍の効果** になることもある。


## 1.3.3 アルゴリズムを評価する指標

- 時間計算量  
- 空間計算量  
- 拡張性（大規模データ時の挙動）  
- 安定性  


# 1.4 レスポンスとスループットの違い

レストランで例えると：

- **レスポンス**：一皿が出るまでの時間  
- **スループット**：1時間に何皿出せるか  

これらは似ているようで全く違う。

例：
- 料理が出るのは早いが、注文数が多すぎて夜間は処理できない → スループット不足  
- 厨房全体の処理量は十分だが、特定料理だけが遅い → レスポンス問題  


# 1.5 アルゴリズムの具体例


## 1.5.1 配列とループ処理
- メモリが連続  
- ランダムアクセスが高速  
- 挿入が苦手（ずらす必要がある）

例：  
本棚に本を差し込むために全てをずらすイメージ。


## 1.5.2 リストとループ処理
- 要素がバラバラに配置  
- ポインタで繋ぐ  
- 挿入・削除が高速  
- ランダムアクセスが遅い


## 1.5.3 ツリーと探索
階層構造。

例：会社の組織図。  
目的の社員（ノード）を効率よく辿れる。

二分探索木なら **探索 O(log n)**。


## 1.5.4 ハッシュアルゴリズム
キーから一瞬で答えが出る。

例：ロッカー番号で荷物を特定する。

- 平均 O(1)  
- 衝突すると遅くなる


## 1.5.5 キュー（FIFO）
行列と同じ。

- 先に来たものから処理  
- 待ち行列の基礎理論に関係


## 1.5.6 スタック（LIFO）
皿の積み重ね。  
後から乗せたものから取り出す。


## 1.5.7 QuickSort
分割統治の代表的ソート。

- 平均 O(n log n)  
- 最悪 O(n²)


## 1.5.8 キャッシュ（1）write back

- 書き込みをキャッシュに保持  
- 後でまとめてディスクに書く  
- 高速  
- 停電リスク（不揮発化で解決）


## 1.5.9 キャッシュ（2）write through

- 毎回ディスクにも書く  
- 一貫性は高い  
- write back より遅い


## 1.5.10 ロックとパフォーマンス

複数処理が同じリソースを使うときの排他制御。

例：  
1本のペンを皆で取り合ってる状態。

- ロックが多い → 待ち時間増加  
- ロック粒度を小さくする技法が重要  


# 第2章 パフォーマンス分析の基本（詳細版）


# 2.1 パフォーマンスの第一歩は測定から

改善の前に **必ず現状を測る**。

- 何が遅いのか  
- どのリソースが詰まっているのか  
- どのタイミングで遅いか  

測定なしに「勘」で修正すると100%失敗する。


# 2.2 必要なパフォーマンス情報とは


## 2.2.1 「はさみうち」の原則

1つの情報だけを見ると間違う。

例：  
CPU 90% → 「重い」ではなく、

- プロセスはどれ？  
- I/O待ちか？  
- キャッシュミスか？  
- ネットワークか？  

“複数方向から攻める” のがパフォーマンス分析の基本。


## 2.2.2 パフォーマンス情報の3種類

1. **OSの情報（CPU・メモリ・IO）**  
2. **ミドルウェアの情報（DB、Webサーバ）**  
3. **アプリのログ・メトリクス**

この3つが揃うことで初めて特定が可能。


## 2.2.3 システムのモデルとトラブル時の動き

システムを下記のようにモデル化する：

ユーザー → LB → AP → DB → ストレージ

どこにキューが溜まるかを推測することで  
ボトルネックが推定できる。


## 2.2.4 データの種類と分析のコツ

- 平均値は嘘をつく  
- 90パーセンタイルを見る  
- 最大値も確認  
- 分布を見る  

例：  
平均5msだが、1秒の遅延が100回に1回あるとユーザー体感は「遅い」。


# 2.3 パフォーマンス分析で重要な理論


## 2.3.1 待ち行列理論の用語

- λ（ラムダ）＝到着率  
- μ（ミュー）＝処理率  
- ρ（ロー）＝使用率  
- 平均待ち時間  


## 2.3.2 平均待ち時間の計算

使用率が高まると待ち時間は **指数的に増加** する。  
CPU80％超えたあたりから急激に遅くなる理由。


## 2.3.3 使用率と待ち行列の例

例：レジが1台の場合

- レジ処理が速くても、客が大量に来たら列が発生  
- 列が伸びると待ち時間も増える  

CPU/IOもこれと同じ。


## 2.3.4 実際にどのような情報を取得するか

- CPU使用率  
- Run Queue（CPU待ち行列）  
- コンテキストスイッチ  
- メモリの使用量・スワップ  
- IO待ち（iowait）  
- ネットワーク遅延  
- ログの処理時間  


# 2.4 OSのコマンド

以下はLinux中心にまとめる：


## 2.4.1 sar
履歴ベースのCPU・メモリ・IOを取得。


## 2.4.2 vmstat
プロセス、メモリ、IOの現在値。


## 2.4.3 ps
プロセスのCPU、メモリ使用率。


## 2.4.4 netstat
接続数、通信状況。


## 2.4.5 iostat
ストレージのIOPS、レイテンシ。


## 2.4.6 top
リアルタイム表示。


## 2.4.7 パケットダンプ（tcpdump/wireshark）
通信内容の確認。


## 2.4.8 pstack
プロセスのスタックトレース。


## 2.4.9 strace
システムコールを追跡して動きを把握。


## 2.4.10 プロファイラ
アプリ内部の処理時間分布を取得。


## 2.4.11 Windowsの場合
- リソースモニタ  
- パフォーマンスモニタ  



# 第3章 実システムのパフォーマンス分析（詳細版）

本章は “実際のシステムで何が起きているかを読み解く力” を鍛える章。  
初心者でもここを理解すると、現場で“パフォーマンスが読める人”になれる。


# 3.1 Web/APサーバとJava/Cアプリ

Webシステムには主に以下の層がある：

```
クライアント → LB → Webサーバ → APサーバ → DB → ストレージ
```

遅くなる原因は必ずどこかの層にあるため、  
層ごとにログやデータを確認する必要がある。


## 3.1.1 Webサーバのアクセスログ解析

代表的なログ：

- Apache：`access_log`
- Nginx：`access.log`

見るポイント：

1. **処理時間（request_time）**  
   どのURLが遅いか。

2. **ステータスコード（5xx, 4xx）**  
   エラーの有無。

3. **どのIPからどれだけ来ているか**  
   高負荷IPを発見できる。

4. **分単位のトラフィック（RPS）**  
   秒間リクエスト数の増加で遅くなることもある。

例え話：  
「レストランの注文票がアクセスログ」  
→ 何の料理を何時に出したか全部書いてある。


## 3.1.2 APサーバのログ（Java/C）

Javaでは：

- GCログ  
- スレッドダンプ  
- アプリ独自ログ（処理時間）

Cアプリでは：

- strace  
- CPUプロファイル  
- ログ出力

特に重要なのは **処理時間の計測ポイントをアプリ側に仕込んでいるか**。

例：注文が遅い場合、どの工程（下ごしらえ・焼き・仕上げ）が遅いか把握するための計測器が必要。


# 3.2 DBサーバのパフォーマンス測定

DBはシステムの最後の砦であり、最もボトルネックになりやすい。


## 3.2.1 DBMSの測定のセオリー

測るポイントは次の3つ：

### ① SQL単位の処理時間

遅いSQLを特定することが最優先。

- 実行計画
- インデックスの有無
- 統計情報
- フルスキャン or 範囲スキャン

### ② リソース状況（CPU・IO）

- CPU100%  
- IO待ち（iowait）  
- デッドロック  

### ③ 接続数・待ち行列

接続が詰まりはじめると、アプリ全体が遅くなる。

例：  
レストランの厨房（DB）は、1分間に10皿しか作れないのに  
注文が50件来ると破綻する。


## 3.2.2 パフォーマンス分析の仕上げ

- インデックス最適化  
- クエリのリファクタリング  
- キャッシュ導入（Redisなど）  
- バッチ処理の時間帯見直し

“SQLの改善” はシステム高速化の最も効果の高い手段の1つ。


# 3.3 ストレージのパフォーマンス分析

ストレージは **IOPS（1秒あたりのIO回数）** が命。


## 3.3.1 ストレージの用語

| 用語 | 意味 |
|------|------|
| IOPS | 1秒間に何回の読み書きができるか |
| 帯域 (MB/s) | 1秒に何MB読めるか |
| レイテンシ | 1回の読み書きにかかる時間 |
| ランダムIO | バラバラのデータを読む |
| シーケンシャルIO | 連続したデータを読む |


## 3.3.2 IOは「速さ」ではなく「量」が大事

例え話：  
水道の水圧（レイテンシ）より、家全体にどれだけ水を送れるか（IOPS）が重要。


# 3.4 ネットワークのパフォーマンス分析

遅い原因の多くは次の3つ：

1. **帯域不足**（道路の幅が狭い）  
2. **遅延（レイテンシ）**（距離が遠い）  
3. **パケットロス**（荷物が途中で落ちる）

ツール：

- ping：遅延  
- traceroute：経路  
- netstat：接続数  
- tcpdump：内部の通信内容  


# 3.5 原因調査（新人が最もつまずく部分）


## 3.5.1 初心者が陥りがちな罠

1. CPU100%＝悪い と勘違いする  
2. DBが遅い＝DBが悪い と勘違いする  
3. ネットワークを疑わない  
4. 特定URLだけ遅いのに全体を疑う  
5. ログを読まない  
6. 一発の測定で判断する


## 3.5.2 心がけるべき姿勢

- 仮説 → データ → 検証  
- 何を疑うかの順番を決める  
- 情報を組み合わせて判断する  


## 3.5.3 実際の調査の流れ

1. **症状の整理**  
2. **再現性の確認**  
3. **ログ分析**（Web/AP/DB）  
4. **OSレベルの分析**（CPU、メモリ、IO）  
5. **ネットワーク確認**  
6. **仮説検証**  
7. **改善策提示**


# 第4章 パフォーマンスチューニング（詳細版）


# 4.1 パフォーマンスとチューニング

チューニングは **調査7割・設定変更3割**。

多くの初心者が真逆で、いきなり設定変更しがち。


## 4.1.1 現実のパフォーマンスとは？

理論値と実測値は違う。

例：CPU 10GHz相当でも  
- IO待ち  
- ロック待ち  
- ネットワーク待ち  
が発生すれば全く速くならない。


## 4.1.2 大局観を持つべし

局所最適は全体最適ではない。

例：  
DBだけ速くしてもアプリが遅ければ意味がない。


# 4.2 パフォーマンスチューニングの定石


## 4.2.1 設定は大きすぎても小さすぎてもダメ

- キャッシュ：大きすぎるとメモリ不足  
- スレッド数：増やしすぎるとコンテキストスイッチ増加  

中庸（バランス）が最も大事。


## 4.2.2 チューニングは1つずつ進める

複数変更すると  
**何が効いたのか分からなくなる**。


## 4.2.3 再利用して速くする

- コネクションプール  
- キャッシュ  
- メモリ再利用  

作業工程を減らすのが目的。


## 4.2.4 まとめて処理する（集約・ピギーバック）

まとめて処理すれば往復回数が減り高速化。

例：  
注文を1皿ずつ持っていくのではなく、まとめて運ぶ。


## 4.2.5 高速化と並列化

- スレッド増加  
- マルチプロセス  
- 並列アルゴリズム

ただし、同期コストに注意。


## 4.2.6 スケールアップとスケールアウト

| 種類 | 内容 |
|------|------|
| スケールアップ | サーバ性能を上げる |
| スケールアウト | 台数を増やす |

クラウド時代はアウトが主流。


## 4.2.7 局所性（Locality）

CPUは「近いデータ」を高速に扱える。

- 時間的局所性（直前使ったデータをまた使う）  
- 空間的局所性（近いアドレスを読みやすい）

アルゴリズム設計の中心概念の1つ。


# 4.3 現場で用いられるテクニック（詳細）


## 4.3.1 ループの省略・キャッチボールの削減

- DBへの往復回数を減らす  
- ネットワーク通信回数を減らす  

例：  
毎回1件ずつSQL発行 → **バルクINSERT** に変更。


## 4.3.2 高頻度データをKVストア化 or ハッシュ化

- Redis  
- Memcached  

これでDB負荷が劇的に減る。


## 4.3.3 「使う場所の近くに置く」

- キャッシュ  
- ローカルストレージ  
- CDN  

Webで最も効果が高い。


## 4.3.4 同期を非同期に変える

- メール送信  
- 通知処理  
- バッチ処理

キュー（RabbitMQなど）を使う。


## 4.3.5 帯域制限

ネットワーク混雑を防ぐため  
意図的に通信量を減らす。


## 4.3.6 LRU方式

Least Recently Used。  
最近使ったものを残し、古いものから捨てる。


## 4.3.7 処理の分割・ロックの粒度調整

ロックが大きいと待ちが増える。

- テーブルロック → 行ロック  
- 行ロック → カラムロック  

と細かくする。


## 4.3.8 不揮発ライトバックキャッシュ

停電でも消えないキャッシュで高速化。


## 4.3.9 マルチレイヤキャッシュ

L1（プロセス内）  
L2（Redis）  
L3（DB）  
など。


## 4.3.10 ジャンボフレーム・高速ネットワーク

データを一度に大量転送する。


## 4.3.11 負荷分散・ラウンドロビン

LBで処理を分散。  
スティッキーセッションはメリットデメリットあり。


## 4.3.12 アフィニティ・バインド

プロセスを特定CPUに固定することで  
キャッシュヒット率を上げる。


## 4.3.13 Copy on Write（COW）

コピーを遅延させる技法。  
メモリ節約。


## 4.3.14 ジャーナル・ログ

安全性のためにログを書きつつ高速化。


## 4.3.15 圧縮

データ転送量を減らすために利用。  
CPUとのトレードオフ。


## 4.3.16 楽観的ロック

競合が少ない場合に有効。  
衝突したときだけ再試行する。


## 4.3.17 カラムナデータベース

列指向DB。  
分析処理に最適。


## 4.3.18 サーバ設定は初期値=最大値の罠

初期値は安全側に寄っている。  
最大性能が出る設定ではない。


# 4.4 実務で遭遇するパフォーマンス


## 4.4.1 パフォーマンス比較の参考

マシン性能差を正しく考慮する。


## 4.4.2 キャッシュヒット率が高くても遅い場合

- そもそも計算が重い  
- キャッシュの中身が巨大  
- ロック競合  


## 4.4.3 ストレージのチューニング方針

IOPSか帯域か、どちらを優先するか。


## 4.4.4 サイズは足りているのにディスク追加

IOPS稼ぐためにディスクを増やす。


## 4.4.5 パフォーマンス観点でのファイル分割

大きいファイルは遅い。  
分割することで並列読み込み可能。


## 4.4.6 90パーセンタイル

平均ではなく “ほとんどのユーザーが体感する性能” を見る。


## 4.4.7 読み込み・書き込み比率

DBの最適化に直結。


# 4.5 チューニング例


## 4.5.1 二重ループ中のSELECT

1000×1000回 = 100万回  
→ DB死ぬ

改善：
- 事前にデータ取得  
- ハッシュマップ化  
- JOINを使う

# 第5章 パフォーマンステスト（詳細完全版）

パフォーマンステストは「性能が運用に耐えられるか」を確認する工程であり、  
**性能要件を満たせない場合は“リリース不可”になるほど重要**。


# 5.1 パフォーマンステストの概要

## 5.1.1 プロジェクト工程における位置づけ

パフォーマンスは基本的に**総合テスト（システムテスト）**で実施され、  
前段階の設計・開発・結合テストの成果が反映される。

位置づけとしては：

```
要件定義 → 基本設計 → 詳細設計 → 開発 → 結合テスト → 総合テスト（ここで性能テスト）
```

性能問題が発覚すると、  
**DB設計・アプリ構造・インフラ構成のすべてに影響する**ため非常に重い。


## 5.1.2 役割に応じたパフォーマンステストの関わり方

| 役割 | 考える内容 |
|------|------------|
| インフラ担当 | CPU/メモリ/IO/ネットワークのボトルネック |
| DB担当 | SQLの性能・インデックス設計 |
| アプリ担当 | 処理時間・ループ・キャッシュ |
| PM（管理者） | スケジュール管理・品質判断 |
| テスト担当 | テストシナリオ作成・実行・計測 |


# 5.2 よくある失敗：9つのアンチパターン

ほぼすべての失敗は、以下のいずれかに該当する。


## 5.2.1 期間内に終わらない！

原因：
- シナリオが多すぎる
- 環境準備不足
- ログ分析ができない

対策：
- 実施順序（必須 → 重要 → 任意）の優先度付け  
- 自動化ツールの利用  


## 5.2.2 パフォーマンスが出ない！ 問題が解決できない！

原因：  
- 測定ポイント不足  
- ログ情報不足  
- 大局観がない

対策：  
- OS → ミドル → アプリの三層を同時に測定する  
- ログを増やし、処理時間を可視化する  


## 5.2.3 環境差異の無視

本番と違う環境でテストしても意味がない。

例：
- ストレージが本番より速い  
- CPUが小さすぎる  
- ネットワーク構成が違う


## 5.2.4 負荷シナリオ不備

実際のユーザー行動を反映していない。

例：  
ユーザーは1分間に3回しか操作しないのに  
“0秒間隔で連打” のテストをしている。


## 5.2.5 バッファ／キャッシュを考慮しない

キャッシュが効く1回目のテストだけ速い → 2回目以降激遅。  
よくある。


## 5.2.6 シンクタイムを考慮しない

シンクタイム＝ユーザーの思考時間。  
実際のユーザーは連打しない。


## 5.2.7 報告内容が理解できず顧客が納得しない

説明能力不足。  
「なぜこの性能なのか」を説明できないと信頼されない。


## 5.2.8 不信感により顧客が納得しない

- 情報共有不足  
- ログ不足  
- テストの透明性不足  


## 5.2.9 テストに時間がかかる

- データ作成が巨大  
- ログが膨大で分析できない  
- 自動化がない  


# 5.3 パフォーマンステストの種類

## 5.3.1 実施のサイクル

```
測定 → 課題分析 → 修正 → 再測定
```

最低3回は回すべき。


## 5.3.2 狭義のパフォーマンステスト（応答時間）

URLごとのレスポンスを見る。


## 5.3.3 限界テスト

- システムが耐えられる最大負荷  
- 限界を超えた時の振る舞い（縮退動作）  
- 障害時の耐性


## 5.3.4 基盤パフォーマンステスト

OS・ネットワーク・ストレージの性能確認。


## 5.3.5 アプリ単体パフォーマンステスト

小さな処理（メソッド単位）で性能を測る。


## 5.3.6 耐久テスト（Long Run Test）

数時間〜数十時間、連続で負荷をかける。  
メモリリーク発見に効果的。


## 5.3.7 隣接分野

- セキュリティ  
- 障害復旧テスト  
- フェイルオーバ  


# 5.4 プロジェクト工程で考えるパフォーマンステスト


## 5.4.1 要件定義

性能要件を具体的に定義：

- 平均レスポンス  
- 最大レスポンス  
- スループット目標  
- 同時接続数  


## 5.4.2 プロジェクト企画

性能テストに必要な予算・期間を確保。


## 5.4.3 【基本設計】システム選定

## 5.4.4 【基本設計】パフォーマンステスト環境

本番に近い構成にすべし。  
特にストレージとネットワーク。


## 5.4.5 その他、性能設計で決めること

- キャッシュ方式  
- 非同期化ポイント  
- DBシャーディング  
- スケールアウト方式  


## 5.4.6 テストスケジュール詳細

最も重いテストは最後に。


## 5.4.7 人員手配と連絡体制

性能問題は全レイヤに跨るため  
関係者とすぐ連携できる体制が必要。


## 5.4.8 基盤結合テスト

OS・ネットワーク・DBの繋ぎ込み。


## 5.4.9 結合テスト（多重実行）

複数ユーザーの同時アクセスに耐えられるか。

負荷・限界・耐久がここに含まれる。


## 5.4.11 運用テスト

## 5.4.12 納品

性能テスト報告書の提出。


## 5.4.13 運用

## 7.1.1 なぜ遅いと言われるのか？

- 物理場所が遠い  
- ベンダー内部でリソース競合

- ノイジーネイバー問題  


# 7.2 クラウドとオンプレの違い


## 7.2.1 クラウドの定義

- オンデマンド  
- スケールアウト可能  
- 使用料課金  


## 7.2.2 オンプレから変わる点

- 構成が動的に変わる  
- OSパッチなどが勝手に当たる  
- ネットワークが複雑  
- ストレージが分散  


## 7.2.3 実装形態

- リージョン  
- アベイラビリティゾーン  
- VPC  


## 7.2.4 サービス分類

- IaaS  
- PaaS  
- SaaS  


## 7.2.5 変動要素と固定要素

クラウドは常に変動する：

- 基盤のCPUは毎回変わる  
- ネットワーク性能も変動する  


# 7.3 クラウド内部構造とアプリ方式


## 7.3.1 集約 or 分散

クラウドでは **分散が基本**。


## 7.3.2 密結合 or 疎結合
