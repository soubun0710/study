# インフラを支える基本的な理論

今回は、**インフラを支える基本的な理論**を学びましょう。これらの理論は、多くのシステムで共通して重要となる考え方です。

# 直列処理と並列処理

システムの処理方法には様々なパターンがあり、それぞれにメリット・デメリットがあります。</br>
ここでは、基本となる**直列処理と並列処理**の考え方について、具体例を交えながら見ていきましょう。

## 直列処理：1つずつ順番に

処理を**1つずつ順番に**実行する方法です。

**例え話**</br>
スーパーのレジが1台しかなく、みんなが1列に並んで順番を待つ。
- 1番目のお客さん：5分かかる
- 2番目のお客さん：5分かかる（1番目が終わってから開始）
- 3番目のお客さん：5分かかる（2番目が終わってから開始）
- 合計：15分

## 並列処理：複数を同時に

複数の処理を**同時に**実行する方法です。

**例え話**</br>
レジが3台あり、列も3つに分かれて同時に会計が進む。
- 合計：5分（ほぼ3分の1）

## メリット・デメリットと使い分け

| 処理方式 | メリット | デメリット |
|---|---|---|
| 直列処理 | 順序が保証される/設計がシンプル | 時間がかかる/ボトルネックになりやすい |
| 並列処理 | 処理が速い/スケールしやすい | 順序の保証が難しい/同じデータが更新されない工夫（排他制御）が必要 |

**使い分けのポイント**
- 順番が重要な処理や、1つずつ確実に終わらせたい場合は直列処理（例：銀行の振込、在庫管理など）
- 独立した処理を効率よく進めたい場合や、処理速度を上げたい場合は並列処理（例：画像変換、ログ集計、メール送信など）

# 同期処理と非同期処理

直列処理と並列処理の考え方を押さえたところで、今度は**処理の待ち方**に注目してみましょう。</br>
システムでは、ある処理が終わるまで待つ場合もあれば、待たずに次の作業を進める場合もあります。</br>
ここでは、その基本となる「同期処理」と「非同期処理」について、身近な例を交えながら見ていきましょう。

## 同期処理：待つ

ある処理が終わるまで**待つ**やり方です。

```
ユーザー：「注文確定」ボタンをクリック
    ↓
サーバー：データベースに書き込み中…
    ↓
ユーザー：ブラウザはくるくる回り続けて、操作できない
    ↓
サーバー：書き込み完了
    ↓
ユーザー：「ご注文ありがとうございました」と表示
```

## 非同期処理：先に進む

処理の完了を待たずに**次の作業に進む**やり方です。

```
ユーザー：「注文確定」ボタンをクリック
    ↓
サーバー：「受け付けました」と即座に返す
    ↓
ユーザー：即座に「ご注文ありがとうございました」と表示、ページを進める
    ↓
バックグラウンドで：データベース書き込み処理が進む
    ↓
完了したら：メールで通知するなど
```

## メリット・デメリットと使い分け

| 処理方式 | メリット | デメリット |
|---|---|---|
| 同期処理 | 処理の完了を確実に確認できる/順序が明確 | ユーザーやシステムが待たされる/遅く感じる |
| 非同期処理 | ユーザーを待たせずに次の処理に進める/全体の効率が良い | 完了確認やエラー処理が複雑になる/順序の保証が難しい |

**使い分けのポイント**
- **同期処理**：処理の完了を必ず確認したいとき（例：銀行の振込、在庫管理など）
- **非同期処理**：ユーザー体験や全体の効率を優先したいとき（例：画像変換、ログ集計、メール送信など）

**モダンなWebサービスの流行**</br>
最近は非同期にできる処理はできるだけ非同期にするのが主流。ユーザーを待たせない設計が重視されています。

# 順序を管理する仕組み：キューとスタック

システムでは複数の処理やリクエストが同時に発生することがよくあります。</br>
そういった場合、どの順番で処理するかを管理する仕組みが重要になってきます。</br>
ここでは、その代表的な方法である**キューとスタック**について見ていきましょう。

## キュー（FIFO：First In First Out）

キューは**先に入ったものから先に出ていく**仕組みです。</br>
プリンターへ送る印刷ジョブ管理など、順番通りに処理したいときに使われます。

**例え話**</br>
スーパーのレジ
- 先に並んだ人から順番に会計を済ませる
- つまり順番通りに処理される

## スタック（LIFO：Last In First Out）

スタックは**後から入ったものが先に出ていく**仕組みです。</br>
Webブラウザの戻るボタン履歴管理など、直前の操作に戻りたいときに使われます。

**例え話**</br>
積み上げられた本
- 最後に積んだ本が最初に取り出される
- つまり順番を逆にたどって処理される

# 排他制御：データを守る

並列処理や非同期処理など「同時にたくさんの仕事を進める」仕組みを学んできました。</br>
しかし、複数の処理が同時に動くと、**同時に触られては困るデータ**が出てきます。そこで必要になるのが**排他制御**です。

## 排他制御がないとどうなる？：銀行の残高管理の例

銀行の残高管理を例として見ていきましょう。</br>
太郎さんの口座に100万円入っているとします。

```
太郎さんからATMで10万円引き出し：
  1. 残高確認：100万円
  2. 10万円減らす：90万円に変更
  3. DB更新

同時に、給与が自動入金されている：
  1. 残高確認：100万円
  2. 給与50万円加える：150万円に変更
  3. DB更新

結果：150万円になるはずが、場合によっては90万円や150万円になってしまう可能性
```

## 実装方法

このような「同時に触られては困るデータ」を守るために、実際のシステムではどんな仕組みが使われているのでしょうか？</br>
代表的な方法を見ていきましょう。

**ロック（Lock）**
- データを更新するときに「使用中」というマークを付ける
- 他の処理は、そのマークが外れるまで待つ
- 同時にアクセスされないようにするための仕組み

**トランザクション（Transaction）**
- 複数のステップをまとめて1つの処理（不可分な単位）として扱う
- どれか1つでも失敗したら、全体をなかったことにして元に戻す（途中までの処理は反映されない）
- 例えば、「①残高を確認→②引き落とし→③履歴を記録」のうち、②で失敗したら①も③も実行されない
- 処理の途中で失敗してもデータが不整合にならないようにするための仕組み

実際のシステムでは、ロックとトランザクションはよく併用されます。</br>
ロックで排他制御しつつ、トランザクションで一連の処理の整合性を守ります。

# ステートフル vs ステートレス

システムが複数のユーザーや処理から同時にアクセスされても、データの整合性や安全性を守ることができる仕組みについて見てきました。</br>
しかし、現代のWebサービスでは、単純なデータのやり取りだけでなく、「ユーザーごとに違う画面を表示する」「ログイン状態を維持する」「途中の操作を覚えておく」など、より複雑な処理が求められます。</br>
こうした複雑なサービスを実現するには、システムが今どんな状況なのか**状態を覚えている（ステートフル）**必要があります。</br>
一方で、逆にシンプルな仕組みにするのであれば**状態を覚えない（ステートレス）**ようにするべきです。

## ステートフル

ステートフルとは、システムが**利用者の過去の操作や状況（状態）を覚えている**設計のことです。</br>
リクエスト内容は最小で済みます。

**例え話**</br>
病院の受付
- 受付で名前を伝えるとカルテを作ってくれる  
- 診察室では「前回は風邪でしたね」と先生が覚えている  
- 薬局でも「この人はこの薬が必要」と処方箋で判断できる

**Webの例**

```
ユーザーがログイン
    ↓
サーバーがセッション情報を保存（このユーザーはログイン済み）
    ↓
ユーザーが別ページに移動
    ↓
サーバーが「あ、このユーザーはさっきログインした人だ」と認識して個人用の画面を表示
```

## ステートレス

ステートレスとは、システムが**利用者の過去の操作や状況（状態）を覚えない**設計のことです。</br>
仕組みがとてもシンプルになります。

**例え話**</br>
スーパーのレジ
- 買い物をするたびに毎回レジで会計する  
- レジの人は「昨日きゅうりを買った山田さんですね」とは覚えていない  
- つまり毎回今持っている商品だけを見て会計する

**Webの例**

```
ユーザーが「私はユーザー12345です」という情報と一緒にページリクエスト
    ↓
サーバーが「ああ、ユーザー12345か。では〇〇の情報を返そう」
    ↓
ユーザーが「私はユーザー12345です」という情報と一緒にページリクエスト
    ↓
サーバーが「ああ、ユーザー12345か。では〇〇の情報を返そう」
```

### 固定長と可変長

データをどのように扱うのかについて見てきました。</br>
ここからは、そのデータを**どんな形（フォーマット）**で管理するのかを見ていきましょう。</br>
本を本棚に入れるように、システムで扱うデータも定められた入れ物の中に保存する必要あります。</br>
データのフォーマットには**固定長と可変長**があります。

## 固定長：長さが決まっている

データの長さが一定のフォーマットです。</br>
仕切りを動かすことできない本棚のイメージです。

**例**
- 社員番号：8桁固定（12345678）
- 郵便番号：7桁固定（123-4567）

**メリット**
- どのデータがどこにあるかすぐ分かるので処理が速くて単純

**デメリット**
- 必要以上に長さを確保すると無駄が出る
- データが増えたら仕様変更が必要（社員番号を10桁にしたいとなると大変）

## 可変長：長さがバラバラ

データの長さを自由に変えられるフォーマットです。</br>
仕切りを自由に動かせる本棚のイメージです。

**例**
- 名前（田中 vs 田中太郎）
- 住所（東京都 vs 東京都渋谷区道玄坂1-2-3）
- 自由入力コメント

**メリット**
- 必要な分だけ使えるので、無駄が少ない

**デメリット**
- 処理が少し複雑になる（どこまでが1件分かを管理する必要がある）
- データベースの設計が複雑になる可能性

# データ構造：効率的に情報を管理する

データの長さや管理方法について見てきました。</br>
ここからは、データを効率よく扱うための**データ構造**について見ていきましょう。</br>
システムの性能や使い勝手を大きく左右する重要なポイントなので、ぜひイメージしながら読んでみてください。

## 配列：位置でアクセス

メモリ上で**連続した**領域にデータが並ぶ構造です。

**例え話**
- ロッカーの1段目に、1番〜10番まで連番で鍵付きロッカーが並んでいるイメージ。

```
メモリアドレス
100: [データ1]
104: [データ2]
108: [データ3]
...
```

**特徴**
- 「5番目の要素」のように、**位置で素早くアクセスできる**（O(1)の時間計算量）
- 途中で要素を追加・削除するときは、後ろをずらす必要がある

**使い道**
- スコアボード（順位別プレイヤー）
- ピクセルデータ（画像）

## 連結リスト：ポインタでつなぐ

各要素が**次の要素へのポインタ（住所）**を持っている構造です。

**例え話**</br>
宝探しゲーム
- 最初のカードに「次はどこへ行け」と書いてあり、たどっていくと宝にたどり着く。

```
[データ1] → [データ2] → [データ3] → [データ4]
  ポインタで次へ   ポインタで次へ   ポインタで次へ
```

**特徴**
- 途中に新しい要素を挿入するのが得意（ポインタを付け替えるだけ）
- 「5番目の要素」に行くには、1番目から順番にたどる必要がある（O(n)の時間計算量）

**使い道**
- キュー（待機列）
- スタック（戻るボタンの履歴）

## ハッシュ：計算式で位置を決める

キー（IDや名前など）を**計算式（ハッシュ関数）でデータを保存する位置を決める**方法です。</br>
バリュー（実際のデータ）は、その場所にそのまま保存されます。

**例え話**
- 荷物を預けるときに番号札をもらい、戻ってきたときにその番号の棚を直接見る。

```
キー「user_12345」
    ↓
ハッシュ関数で計算（どこに保存するか決める）
    ↓
「保存場所3」と決まる
    ↓
その場所からデータをすぐ取り出せる
```

**特徴**
- うまく設計すれば、とても高速に探せる（O(1)）
- 「衝突」に注意（異なるキーが同じ位置にマップされる可能性）

**使い道**
- ユーザーID検索
- キャッシュ
- Redisなどのキーバリュー型ストレージ

## ツリー構造：階層的に整理

データを木のような構造で管理する方法です。</br>
代表例：二分探索木、B木など

**例え話**
- 「50以上か未満か」「さらに25以上か未満か」…といった具合に、質問を繰り返して探す20問ゲームのようなイメージ。

```
        [50]
       /    \
    [25]    [75]
    / \     / \
  [10][35][60][85]
```

**特徴**
- データが増えても、うまくバランスを保てば効率よく探せる（O(log n)）
- ファイルシステムやデータベースインデックスで使われる

**使い道**
- ファイルシステム（フォルダの階層）
- データベースインデックス（高速検索）
- JSONやXMLのような構造化データ

# キャッシュ：高速化の秘密兵器

データ構造の工夫によって、効率的な管理や高速な検索ができることを見てきました。</br>
しかし、現実のシステムでは「同じデータを何度も参照する」「遠い場所からデータを取ってくると遅い」など、さらに速度を求められる場面が多くあります。</br>
そこで登場するのが**キャッシュ**です。キャッシュとは**よく使うデータを近くにコピーしておくことで、アクセスを速くする仕組み**です。

**例え話**
- よく使う辞書を、毎回本棚から取ってくるのではなく、机の上に置きっぱなしにしておく。

## キャッシュの階層

実は、コンピュータの中には何段階もキャッシュがあります。</br>
コンピュータの中にあるキャッシュを**CPUキャッシュ**といいます。

```
CPU
  ↓
【レジスタ】: 最速
  ↓
【L1キャッシュ（1次キャッシュ）】: 超高速
  ↓
【L2キャッシュ（2次キャッシュ）】: 高速
  ↓
【L3キャッシュ（3次キャッシュ）】: 中速
  ↓
メモリ
  ↓
ストレージ
```

CPUが計算するときはまずL1キャッシュを使い、そこになければL2やL3、さらにメモリやSSDまで探しに行きます。</br>
距離が遠いほど時間がかかるので、よく使うデータはできるだけ上の階層に置いておくのが効率的です。</br>
上に行くほど容量は小さいけど速いし、下に行くほど容量は大きいけど遅いです。

## Webでのキャッシュ例

- **CPUキャッシュ**：CPUのすぐそばにある超高速メモリ
- **Webブラウザキャッシュ**：よく見る画像やCSSをPCに保存しておく（2回目以降のアクセスが速い）
- **アプリケーションキャッシュ**：DBから取った結果をメモリにしばらく保持（同じ検索なら即座に返せる）
- **CDN（Content Delivery Network）**：画像や動画をユーザーに近い場所のサーバーに置いておく

## キャッシュの課題：鮮度の問題

キャッシュは速い反面、古い情報が残ることがあります。</br>
これを**キャッシュ無効化**の問題といいます。

```
キャッシュに「商品Aの価格は1000円」と保存されている
    ↓
データベースの商品Aの価格が800円に更新される
    ↓
ユーザーはキャッシュから「1000円」という古い情報を見てしまう
    ↓
買ったら「あ、実は800円だった」ということになる
```

これを**キャッシュ無効化**の問題といいます。

**対策**
- TTL（Time To Live）：キャッシュに保持時間を設定（5分後に自動削除など）
- イベントベース無効化：データが更新されたら、キャッシュも削除
- キャッシュバースティング：キャッシュバージョンを変更する

## 使い分け

**キャッシュに向いているデータ**
- 参照されることが多いデータ（例：商品情報、ユーザーのプロフィール画像など）
- 失われても問題ないデータ（例：一時的なランキング、検索結果など）

**キャッシュに向いていないデータ**
- 更新が頻繁なデータ（例：リアルタイムで変化する在庫数や取引履歴など）
  - キャッシュの鮮度管理が難しく、最新情報を保証しづらい
- 大量のデータ（例：全ユーザーの全履歴など）
  - キャッシュ容量の制限や管理コストが高くなる

**ポイント**
- キャッシュは「よく読まれるが、あまり書き換えられないデータ」に最適
- 「最新の情報が必要」「データ量が膨大」な場合は、キャッシュより直接データベースを使う方が安全

# 割り込み：優先度の高い処理を先にする

システムにはユーザー操作や外部からの信号など、いつ発生するかわからないイベントもあります。</br>
こうしたイベントに素早く対応するために、**割り込み**という仕組みが使われています。</br>
割り込みとは、**今やっている処理を一時停止して、緊急度の高い処理を先に実行する仕組み**です。

**例え話**
- 事務作業をしているときに、火災報知器が鳴ったら、仕事を中断して避難する。

## 割り込みの仕組み

割り込みは、システムで発生したイベントにすぐ対応するための仕組みです。この割り込みに対応するのはCPUです。

**CPUが受け取る割り込みイベント例**
- キーボード入力（ユーザーがキーを押した瞬間）
- ネットワークカード受信（データが届いた瞬間）
- ディスク読み込み完了（ファイルの読み込みが終わった瞬間）
- タイマー通知（一定時間ごとに処理を実行したい場合など）

これらのイベントが発生すると、CPUは現在の処理を一時停止し、「割り込みハンドラー」と呼ばれる特別な処理を即座に実行します。

# ポーリング：定期的に様子を見に行く

割り込みは何かが発生したら連絡するイベントドリブンな仕組みです。</br>
これに対して**一定間隔で様子を見に行くポーリングという仕組み**もあります。

**例え話**
- 「そろそろ荷物届いたかな？」と、玄関を何度も見に行く。

## ポーリングの特徴
- システム側から一方的に状態を確認する
- 確認は定期的に、決まった間隔で行われる

**メリット**
- 実装がシンプル

**デメリット**
- 無駄な確認が多くなる（何も起きていないのに見に行く）
- 頻度を上げると負荷が高くなる

## 使い分け

**向いている処理**
- 一定の間隔で処理が実行できていればよい処理
    - 例：メール受信確認  
      - メールが届いていなくても、定期的に受信確認を繰り返すだけで問題ない
      - 即時に受信できなくても困らない場合に適している
- 監視
    - 例：サーバーの死活監視  
      - ダウンしたサーバーは自分で「ダウンした」と通知できないため、外部から定期的に状態を確認する必要がある
      - 例えば、数分ごとにpingを送って応答があるか確認する

**向いていない処理**
- 入力内容に応じて実行内容を変える処理
  - キーボードの入力はキーを押された状態によって処理内容が変わるので不向き
- 処理の優先順位付けが必要な処理
  - 定期的な間隔で処理が実行されるので処理の優先度を付けられない

# I/Oサイズ：1回のデータ転送サイズ

割り込みやポーリングといった「いつデータをやり取りするか」という仕組みについて見てきました。</br>
他にも**1回のやり取りでどれだけのデータを扱うか**という視点も重要です。これが**I/Oサイズ**です。</br>
I/Oサイズとは、**1回の読み書きで扱うデータのかたまりの大きさ**です。

※※※ここまで読んだ※※※

**例**
- 4KBずつ読む
- 1MBまとめて読む
- 1GBを一度に転送

#### 倉庫の例え話

倉庫から荷物を運ぶときに：

- 小さい箱を何度も運ぶ：往復の手間が多い（オーバーヘッド大）
- 台車にまとめて載せて運ぶ：効率的

#### トレードオフ

**大きいI/O**
- メリット：1回でたくさん運べる
- デメリット：1発が重い、キャッシュを圧迫

**小さいI/O**
- メリット：細かく運べる、キャッシュメモリに優しい
- デメリット：回数が多い、オーバーヘッド大

#### インフラ設計での考慮

- ストレージやネットワークの特性
- アプリケーションのアクセスパターン
を考慮して、適切なI/Oサイズを選ぶことが重要です。

> **実例**
> - SSD：4KBのランダムアクセスに強い
> - HDD：1MBの順序アクセスに強い

### ジャーナリング：作業ログを先に記録する

ジャーナリングとは、**「何をしようとしたか」をログとして先に書いておく仕組み**です。

#### イメージ

倉庫の在庫を動かすときに：

- やり方1（危険）：
  - 在庫を移動する
  - （途中でトラブル発生）
  - 「あ、途中までしか終わってない。どこまで行った？」

- やり方2（安全）：
  - 伝票に「在庫Aを50個、棚Bから棚Cに移動する」と書く
  - 在庫を移動する
  - （途中でトラブル発生）
  - 伝票を見て「ああ、50個移動しようとしてたんだ。現状を見て判断しよう」

#### ファイルシステムでのジャーナリング

ファイルシステムやデータベースでよく使われます。

**例：ファイルを削除するときに**

```
ジャーナルに「ファイルXを削除する」と記録
    ↓
実際にファイルを削除
    ↓
ジャーナルから削除マークを消す
```

途中でシステムが落ちても：
- 削除ジャーナルがあれば、復旧時に「あ、ファイルXを削除しようとしてたんだ」と分かる
- 削除が完全に終わってなければ、やり直す

**メリット**
- 障害発生時に、処理をやり直したり、巻き戻したりできる
- データの整合性を保ちやすい

> **Durable と Consistent**
> これらは、ACIDトランザクションの重要な要素です。詳しくはデータベース設計の本を参照。

### レプリケーション：データの複製

レプリケーションとは、**データを別の場所に複製する仕組み**です。

#### イメージ

大事な書類を、金庫に1つだけ置いておくのではなく、別の支店にもコピーを保管しておく。

#### レプリケーションの種類

**同期レプリケーション**
- 本体に書き込むとき、同時にコピー先にも書き込む
- データはほぼ完全に一致
- そのぶん遅くなることもある（コピー先のレスポンスを待つため）

```
クライアント：「書き込んで」
    ↓
マスターDB：書き込み中…
    ↓
スレーブDB：書き込み中…
    ↓
両方の書き込みが完了
    ↓
クライアント：「完了」と応答
```

**非同期レプリケーション**
- 本体への書き込みを先に終え、その後でコピーを送る
- 性能は出しやすい
- 障害時に、少しだけ差分が失われる可能性がある

```
クライアント：「書き込んで」
    ↓
マスターDB：書き込き完了
    ↓
クライアント：即座に「完了」と応答
    ↓
バックグラウンド：スレーブDBにレプリケーション送信中…
```

#### 用途

- **バックアップ**：別の場所にデータ複製を保持
- **読み取り負荷分散**：読み取り専用のスレーブを複数用意（書き込みはマスターへ）
- **地理的冗長化**：別のデータセンターに複製（災害対策）

> **高度なトピック**
> - マルチマスターレプリケーション（複数の書き込みポイント）
> - シャーディング（データを分割して複数サーバーに分散）
> など、さらに複雑なトポロジーもあります。

### マスター／ワーカー：仕事を分解して配分する

マスター／ワーカー方式とは、**マスター（司令塔）が仕事を分解し、ワーカー（作業者）に振り分ける**構成です。

#### イメージ

現場監督（マスター）が作業内容を細かく分けて、職人さんたち（ワーカー）に各タスクを割り振る。

#### 流れ

1. **マスター**：「やるべき仕事の一覧」を持つ
   - 10万件のデータ処理が必要
   - 1000件ずつ、100個のタスクに分割

2. **ワーカー** （複数台）：空き時間に「仕事をください」と取りに来る
   - ワーカーA：タスク1（1000件）を処理中
   - ワーカーB：タスク2を処理中
   - ワーカーC：空いてる→「仕事ください」→タスク3をもらう

3. **ワーカー**：仕事を終えたら結果をマスターに報告
   - マスターが進捗を追跡

#### メリット

- ワーカーを増やすことで処理能力を上げられる
- マスターが全体の進捗を管理しやすい
- 負荷分散が自動的に行われる

#### 実装例

- **Hadoop MapReduce**：ビッグデータ処理
- **Apache Spark**：高速データ処理
- **Kubernetes：** コンテナオーケストレーション（複数のワーカーノードを管理）

### 圧縮：データサイズを小さくする

圧縮とは、**データのサイズを小さくする技術**です。

> **例え話**
> 大きな布団を圧縮袋に入れて、小さくして押し入れにしまう。

#### なぜ圧縮するのか

- **通信量を減らす**：ネットワークを通じて送信を速くする
- **ディスク容量を節約**：ストレージを有効活用

#### トレードオフ

- **圧縮・解凍にCPUを使う**
- **圧縮率を上げすぎるとCPU負荷が増える**

#### 実例

- **Gzip**：Webの標準圧縮（HTMLやJavaScriptを圧縮）
- **Brotli**：より高い圧縮率（最近のブラウザが対応）
- **PNG**：画像ファイルの無損失圧縮
- **MP4**：動画の圧縮

### 誤り検出：データが壊れていないか確認する

誤り検出とは、**データが壊れていないかを確認する仕組み**です。

#### イメージ

重要書類を送るときに、「ページ数が全部で10枚です」と書いておき、
受け取った側が枚数を数えて確認する。

#### 代表的な方法

**パリティ**
- 「1の数が偶数になるように1ビット追加しておく」など
- 受信側で数を数えて、合っているか確認
- シンプルだが、エラーの位置は分からない

**チェックサム**
- データ全体から数値を計算し、その値も一緒に送る
- 受信側で同じ計算をして、値が一致するか確認
- より信頼性が高い

**CRC（Cyclic Redundancy Check）**
- より高度なチェックサム
- Ethernet、ファイル転送などで使われる

#### インフラでの利用

- **ネットワーク通信**：イーサネットフレーム、IP パケット
- **ディスクへの書き込み**：ストレージの信頼性向上
- **ファイル転送**：FTP、HTTPでも使われている

## まとめ：インフラの全体像

ITインフラの様々な側面を学んできました。最後に、全体像を整理しましょう。

### インフラの階層

```
【アプリケーション層】
  勤怠管理システム、ECサイト、チャットアプリ など

【ミドルウェア層】
  Webサーバー、アプリサーバー、データベース など

【OS層】
  Linux、Windows Server など

【ハードウェア層】
  CPU、メモリ、ストレージ、ネットワーク など

【データセンター】
  建物、電源、冷却システム、セキュリティ など
```

各層が協力して、初めてシステムが動きます。

### 3つの設計視点

**垂直分割**：処理の流れに沿った階層化
- Web層 → AP層 → DB層
- 責任分担を明確に

**水平分割**：同じ役割を複数化してスケールアウト
- サーバーを並べて、負荷分散
- クラウド時代の主流

**地理分割**：複数の場所に分散
- 災害対策、可用性向上
- RPO/RTO を意識した設計

- でも、その裏には、インフラエンジニアの細かな工夫と最適化がある
- キャッシュの使い方、レプリケーションの戦略、負荷分散の工夫…
