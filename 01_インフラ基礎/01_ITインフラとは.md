# はじめに：ITインフラって何？

皆さんは毎日、様々なWebサービスやアプリケーションを使っていますよね。LINEで友達と連絡を取ったり、YouTubeで動画を見たり、Amazonで買い物をしたり。</br>
こうしたサービスが快適に動作しているのは、実は見えない場所で「インフラ」という仕組みが支えているからです。

## インフラとは「システムの土台」

ITインフラとは、システムやアプリケーションが動くための**根本的な基盤**のことです。</br>
身近な例で考えてみましょう。

- 家を建てるときに必要なもの：土地、基礎工事、電気、水道、ガス
- 会社を運営するときに必要なもの：建物、机、インターネット回線、電話システム

アプリケーション（勤怠管理システム、ECサイト、チャットツールなど）も、これと同じ。いくら素晴らしい機能を作っても、その下にしっかりした「インフラ」がなければ、快適には動きません。

## ITインフラを構成する主な要素

ITインフラを構成する重要な要素を説明します。</br>
ITインフラの全体像をイメージしやすくするため、ここでは「アプリケーション」も含めてまとめていますが、厳密にはアプリケーションはインフラの“上”に乗る存在です。

| ITインフラの要素 | 役割 | 
|---|---|
| サーバー | 処理を実行するコンピュータ |
| ネットワーク | サーバー同士やユーザーをつなぐ仕組み |
| ストレージ | データを保存する場所（HDD、SSDなど） |
| OS（オペレーティングシステム） | サーバーを動かす基本ソフト |
| ミドルウェア | データベースやWebサーバーなど、アプリケーションの土台となる共通機能 |
| アプリケーション | 特定の目的のために作られたソフト（インフラの上で動く） |

# ITインフラ構成の2つの大きな考え方

ITインフラを構成するには、大きく分けて2つの設計スタイルがあります。それぞれの特徴や歴史的な背景もあわせて見ていきましょう。

## 集約型アーキテクチャ：すべてを1台に集約する

昔々、コンピュータはとても高価でした。だから、できるだけ1台で済ませようという発想が生まれます。

**集約型アーキテクチャ**は、1台のとても大きなコンピュータ（メインフレームなど）に、**処理・データ・機能をすべて集約する**やり方です。

### ワンオーナー全部入り店舗の例え話

想像してください。八百屋も電気屋も服屋も、すべてが1つの店の中にあり、同じオーナーが運営しています。レジも在庫管理も同じシステムで一元管理されています。

- **メリット**
  - 一元管理しやすい
  - 高い信頼性と性能を確保しやすい
  - セキュリティポリシーを統一しやすい
  - データの一貫性が保ちやすい

- **デメリット**
  - 初期投資がめちゃくちゃ高い
  - 拡張が難しい（1台をさらに強化する必要がある）
  - 特定ベンダーに依存することが多い
  - 1台が壊れたら大変

### 実例

今でも「絶対に止まってはいけない」「データの一貫性や正確さが最優先」「高いセキュリティや厳格な管理が必要」といったシステムで選ばれています。

- 銀行の勘定系システム（口座管理、送金など重要な機能）
- 大企業の基幹系システム（給与管理、人事管理など）

## 分割型アーキテクチャ：役割ごとに複数のサーバーに分ける

時代が進み、コンピュータが安くなってくると、違う発想が生まれます。</br>
「それぞれの役割に特化した小さなコンピュータを複数台用意して、組み合わせたら効率的じゃないか？」</br>
これが**分割型アーキテクチャ**です。複数のサーバーに役割を分けてシステムを構成します。

### 商店街の例え話

商店街をイメージしてください。八百屋、魚屋、肉屋、パン屋などが並んでいて、それぞれが専門分野を担当しています。お客さんは必要なお店を回ります。</br>
もし枝豆の需要が急に増えたら、八百屋を拡張すればいいだけ。別のお店には影響しません。

- **メリット**
  - スケーリング（「もっと速く」「もっとたくさん同時に」動かせるようにすること）が柔軟
    - 例えば、アクセスが増えたときにサーバーを追加したり、性能を上げたりして対応できる
    - つまり必要な部分だけ増強・拡張しやすいってこと
  - 障害を一部のサーバーに閉じ込めやすい（1つのサーバーが落ちても全体が止まらない）
  - 技術ごとに最適な構成を取りやすい（DBはこのツール、Webサーバーはあのツールなど）

- **デメリット**
  - 全体設計が複雑になりやすい
  - ネットワークや接続方式の設計が重要
  - テスト項目が増える
  - サーバー間の連携を管理する必要がある

**現代のトレンド** </br>
クラウド技術の発展により、今は分割型（分散型）がスタンダードです。</br>
AWSやGCPといったクラウドサービスも、分割型を前提に設計されています。</br>
クラウドでは「必要なときに必要なだけサーバーを増やす」「障害が起きても他のサーバーでサービスを継続する」「世界中のユーザーに素早くサービスを届ける」が求められるためです。</br>
つまり柔軟性（すぐ増やせる）や拡張性（負荷に合わせて広げられる）、可用性（止まらずに使い続けられる）が重要ということです。</br>
1台の大きなコンピュータに頼るのではなく、役割ごとにサーバーを分けておくことで、急なアクセス増加や障害、グローバル展開にも強い仕組みを作ることができます。

### 実例

- ネットショッピングサイトで「商品を表示するサーバー」「注文を受け付けるサーバー」「データを保存するサーバー」でサーバーを分ける
- マイクロサービスという考え方もあり、「会員登録」「商品検索」「注文処理」などの小さなサービスに分けて作り、それぞれが独立して動きながらお互いに連携してサービス全体を作り上げる

# システムを「分割」する3つの軸

前述したとおり、現在のITサービスやクラウドの多くは、柔軟性や拡張性、障害への強さなどの理由から「分割型（分散型）」が主流となっています。</br>
そのため、これからは分割型アーキテクチャをさらに詳しく見ていきましょう。</br>
分割型アーキテクチャは、さらに3つの分割方法に分けられます。これを理解することで、複雑なシステム設計が見えてきます。

## 垂直分割：処理の流れに沿って階層ごとに分ける

**垂直分割**は、**処理の流れに沿って役割を階層ごとに分ける**考え方です。</br>
想像しやすい例として、**3階層型システム**を見てみましょう。

### レストランで説明するとわかりやすい

1. **注文を取る係（ホール）** → ユーザーインターフェース層
2. **調理をする係（キッチン）** → アプリケーション層
3. **在庫や売上を管理する人（バックオフィス）** → データ層

それぞれが自分の役割に集中することで、全体として効率よく回ります。

### 3階層型システムの詳細

Webシステムは、よく次の3つの階層に分けられます。

```
[ユーザーのブラウザ]
        ↓
   【Web層】
        ↓
   【AP層】
        ↓
   【DB層】
```

**Web層（プレゼンテーション層）**
- ユーザーのブラウザからのリクエストを受け取る玄関口
- HTMLや画像をユーザーに返す
- 見た目や表示形式を担当

**AP層（アプリケーション層）**
- ビジネスロジック（複雑な計算や判断）を実行する
- 「このユーザーは注文できるか？」「在庫はいくつ残っているか？」などを判断
- Web層とDB層の橋渡し役

**DB層（データ層）**
- データベースを操作し、データの保管・検索・更新を行う
- 企業の重要な資産（顧客情報、商品情報、売上記録など）を管理

### ECサイトで商品を検索するときの流れ

実際にどのように動くのか具体例で見ていきましょう。

1. **ユーザーのブラウザ**
   - 「スニーカー」というキーワードを検索ボックスに入力
   - 「検索」ボタンをクリック
   - この操作で、検索条件（例：スニーカー）をサーバーに送信する

2. **Web層**
   - ユーザーからのリクエスト（「スニーカーを検索したい」）を受け取る
   - AP層（アプリケーション層）に「スニーカー検索」の処理を依頼する

3. **AP層**
   - 検索条件（スニーカー）をチェック
   - DB層に「スニーカーの商品一覧をください」と問い合わせる
   - もしユーザーが「価格が安い順に並べたい」「在庫がある商品だけ表示したい」などの追加条件を選んでいた場合は、その条件も含めてDB層に問い合わせる

4. **DB層**
   - 商品データベースから「スニーカー」に該当する商品を検索
   - 検索結果（商品リスト）をAP層に返す

5. **AP層**
   - DB層から受け取った商品リストを、ユーザーのリクエスト内容に合わせて整形する
   - 例えば、ユーザーが「価格順に並び替えたい」「レビューや星評価も見たい」と指定していた場合は、その条件に従って並び替えや情報の追加を行う

6. **Web層**
   - AP層から受け取ったデータをHTMLとして整形し、ユーザーのブラウザに返す

7. **ユーザーのブラウザ**
   - 検索結果ページが表示される（スニーカーの商品一覧が見える）

このように、3つの層が協力して1つの処理を完成させるわけです。

### 垂直分割のメリット・デメリット

- **メリット**
  - 役割が分かれているので、責任範囲が明確
  - 層ごとに技術や製品を選べる（画面はWebブラウザ、ロジックはJava、データはPostgreSQL、など）
  - 障害解析がしやすい（どの層で止まっているか特定しやすい）
  - チームごとに役割分担しやすい

- **デメリット**
  - 層をまたぐ通信が増える（そのぶん少し遅くなる可能性）
  - 設計が悪いと層間の呼び出し（ある層から別の層に処理やデータのやり取りを依頼すること）が複雑化してしまう

## 水平分割：同じ役割のサーバーを横に増やす

前述の方法とは別に、システムを拡張するもう1つの考え方として、**水平分割**があります。</br>
水平分割は、**同じ役割のサーバーを横に増やしていく**考え方です。

### レジの例でわかりやすく

スーパーのレジを想像してください。

- レジが1台だけ → 行列ができる、待ち時間が長い
- レジを3台に増やす → 行列が3つに分散、お客さんがスムーズに会計できる

これと同じことを、Webサーバーやアプリサーバーでやるわけです。

### 実例

- Webサーバーを複数台にして、ユーザーからのアクセスを均等に振り分けて負荷分散する
  - 例：たくさんの人が同時にWebサイトを見るとき、1台だけだと混雑するので、複数台で分担して処理する
- アクセスが急増したとき、同じ役割のサーバーを必要な数だけ増やして対応する
  - 例：イベントやセールでアクセスが増えた場合、サーバーを追加して全体の処理能力を上げる
- バッチ処理を複数サーバーで並列処理する
  - 例：大量のデータを夜間にまとめて処理するとき、1台でやるより複数台で同時に作業すると早く終わる

### スケーリングの2つの方法

ここまで、同じ役割のサーバーを複数台並べて負荷分散したり、アクセス増加に対応する方法を紹介しました。</br>
こうした「サーバーを増やしてシステムの処理能力を上げる」ことを、前述した通り**スケーリング**と呼びます。</br>
スケーリングには大きく2つの方法があります。それぞれの違いと特徴を詳しく見ていきましょう。

**スケールアップ**：1台のサーバーを強くする
- CPUを追加
- メモリを増設
- 単純だけど、コストが高くつく
- 1台には物理的な限界がある（CPU数は有限、メモリサイズも有限）

**スケールアウト**：同じサーバーを複数台に増やす（水平分割）
- 複数台の同じサーバーを並べる
- クラウドでは安価に追加できる
- 複数台を管理するしくみが必要
- 無制限に増やせる（理論的には）

**現代のクラウド時代では、スケールアウトを前提に設計することが主流です。**</br>
AWSやGoogle Cloud、Azureなどのクラウドサービスは、スケールアウトに最適化されています。（スケールアウトしやすいように作られている）</br>
もちろんスケールアップも可能ですが、スケールアップには限度があるので、一般的にはスケールアウトが主流だということです。

## 地理分割：複数の場所にシステムを分散配置する

最後の分割方法は、**地理的な視点**です。</br>
**地理分割**は、地理的に離れた場所にシステムを分散配置する考え方です。

### 実例

- 東京のデータセンター + 大阪のデータセンター
- 日本の東日本リージョン + 西日本リージョン
- アメリカの東海岸 + 西海岸

### 会社の支店の例え話

会社が全国に支店を持つとします。</br>
もし東京の本店が災害で機能しなくなってしまっても、大阪支店が代わりに業務を続けられます。</br>
このように、どこかが止まっても全体が止まらない仕組みを作るのが地理分割の目的です。

### 目的

- **災害対策**：地震、停電、火災など、物理的な災害からシステムを守る
- **可用性向上**：どこかのデータセンターが落ちても、別のデータセンターでサービスを継続できるようにする
- **レイテンシ削減**：ユーザーに近い場所にサーバーを置くことで、応答速度を向上させる
- **ライセンス対応**：データを国内に保管する必要がある場合など、法的要件に対応する

### RPOとRTO：覚えておくべき2つの指標

地理分割には様々な目的がありますが、実際に設計する際には「どこまでの障害なら許容できるのか？」を事前に決めておく必要があります。</br>
その判断材料として使われるのがRPOとRTOの2つの指標です。

**RPO（Recovery Point Objective）**：「どこまでデータを戻せればよいか」という目標
- 例：「最悪、5分前まで戻せればよい」（5分以上前のデータは失われてもいいという意思決定）
- RPOが小さいほど（例：1時間より5分のほうが小さい）、より頻繁にバックアップする必要があり、コストが高くなる

**RTO（Recovery Time Objective）**：「復旧にどれくらい時間をかけてよいか」という目標
- 例：「1時間以内にサービスを再開したい」
- RTOが小さいほど（例：24時間より1時間のほうが小さい）、災害対応に費用がかかる
- リアルタイムレプリケーションなど、高度な技術が必要になる

銀行などの重要なシステムは、RPOもRTOも非常に小さく設定されます。一方、内部用の管理システムなら、もっと緩い値でも問題ない場合があります。

# 物理的なハードウェアを理解しよう

ここまで、システム全体の設計や運用の考え方について学んできました。</br>
ここからは視点を変えて、「実際にどんなハードウェアがシステムを支えているのか」を見ていきましょう。</br>
まずは、データセンターなどで使われる物理サーバーの形や特徴について説明します。

## ラックマウント型サーバー

データセンターにあるサーバーは、多くの場合 **ラックマウント型** という独特の形をしています。

- 薄い「引き出し」のような形
- 身近な例でいうと、オフィスの棚にぎゅっと並べたファイルボックスみたいな感じ
- 高さの単位は「U（ユー）」で表示（1U、2Uなど）
- 1Uは約4.4cm

これらを縦長のラックに何十台も積み重ねて設置します。

### なぜこんな形？

効率よく大量のサーバーを並べて運用できるようにするためです。</br>
しかし、メーカーごとにサイズがバラバラでは効率化できません。そこで、世界中のメーカーが同じ形・同じサイズで作るための規格（EIA‑310）が生まれました。

- 限られたスペース（データセンターの床面積）に、多くのサーバーを収容できる
- 配線（電源、ネットワークケーブル）を整理しやすい
- 空気の流れ（前吸気・後排気）が一定になり、冷却効率が高い

## CPU：コンピュータの頭脳

ラックマウント型サーバーの特徴を見てきましたが、サーバーは「箱」だけでは動きません。</br>
その中には、様々な電子部品が組み込まれています。</br>
ここからは、サーバーの心臓部ともいえるCPUについて詳しく見ていきましょう。

### CPUの役割

CPU（Central Processing Unit）は、コンピュータの**頭脳**です。</br>
すべての計算や命令の実行、データの処理はこのCPUが担当します。</br>
アプリを動かしたり、データを計算したり、ファイルを開いたりするたびに、CPUが「どう動くか」を判断し、実際に処理を進めています。

**例え話**</br>
会社でいうと、CPUは「社長」や「司令塔」のような存在。</br>
どの仕事を誰に割り振るか、どんな順番で進めるかを決めて、全体を動かしています。

### クロック周波数：処理のスピード

**クロック周波数（GHz）**は、「1秒間に何回、処理の拍（クロック）を刻めるか（命令を実行できるか）」という指標です。</br>
この値が高いほど、CPUは短い時間でたくさんの処理をこなせます。

- 3.0GHz = 1秒間に30億回の計算ができる
- 周波数が高いほど、1つ1つの処理が速く終わる
- ただし、周波数を上げすぎると発熱が増え、冷却が大変になる（冷却コストが増える）

**例え話**</br>
スポーツ選手で説明すると、同じ腕の動きでも、1秒間に何回も振れる人 vs ゆっくり振る人。速く振れる人の方が、短時間にたくさんの動作ができます。

### コア数：同時処理の能力

**コア数**は、「CPUの中に脳みそが何個分あるか」という指標です。</br>
1コアなら1つの仕事しか同時にできませんが、コアが増えるほど、同時にたくさんの処理ができます。</br>
コアが処理する単位をスレッドといいます。

- 1コア = 1つのことしか同時にできない（1つのスレッドしか動かない）
- 8コア = 8つのことを同時にできる（8つのスレッドが動く）
- サーバー用CPUでは16コア、32コア、64コアなども珍しくない

**例え話**</br>
従業員の数で考えると、1人は1つのことしかできません。同時に複数の仕事をこなしたいなら、従業員を増やす必要があります。

### マルチコアの時代

昔は「1つのCPU＝1コア」でしたが、今は1つのCPUの中に複数のコアが入っています。</br>
これを**マルチコアCPU**と呼びます。</br>
OS（オペレーティングシステム）は、実行中のプログラム（プロセス）を複数のコアにうまく割り振って、効率よく同時並行で処理を進めます。

**具体例**</br>
ゲームを動かす場合：ゲーム本体の処理を4コア、映像描画を2コア、音声処理で2コア…というように役割ごとにコアを分担して同時に動かすことができます。

## メモリ：作業用の机

CPUが処理するときに使う一時的な置き場所、それが**メモリ（RAM）**です。

### メモリのイメージ

メモリは「作業机の広さ」に例えると分かりやすいです。

- **メモリが広い（多い）ほど**
  - 机が大きいので、一度にたくさんの資料（データ）を広げて作業できる
  - たくさんのアプリやデータを同時に扱っても、スムーズに仕事が進む

- **メモリが狭い（少ない）と**
  - 机が小さいので、必要な資料を何度も本棚（ストレージ）に取りに行く必要がある
  - その度に時間がかかるので、全体的に作業が遅くなる

### メモリの重要な特性

メモリは**揮発性**です。つまり、電源を切るとすべてのデータが消えてしまいます。</br>
そのため、作業中のデータを長く残したい場合（重要なデータなど）は、ストレージ（HDDやSSD）に保存する必要があります。

### メモリとストレージの違い

この2つはよく混同されますが、役割も性質も大きく異なります。

| 項目 | メモリ（RAM） | ストレージ（HDD/SSD） |
|---|---|---|
| **用途** | 作業中の一時的な置き場所 | 長期保管 |
| **速度** | とても速い（ナノ秒単位） | 遅い（ミリ秒単位） |
| **電源OFF時** | 消える（揮発性） | 残る（不揮発性） |
| **容量** | 少ない（8GB〜256GB程度） | 多い（1TB以上） |
| **用途例** | アプリの処理中のデータ | OS、アプリ、写真、動画など |

**ポイント**</br>
メモリは「今だけ使う高速な作業場」、ストレージは「長期間しまっておく倉庫」です。

### ROM：電源を切っても消えないメモリ

実は、コンピュータにはもう1種類のメモリがあります。</br>
**ROM（Read-Only Memory）**は「読み取り専用メモリ」で、マザーボードやデバイスに組み込まれている**不揮発性メモリ**です。</br>
※マザーボードとは、CPUやメモリなど主要な部品が取り付けられているコンピュータの土台となる基板のことです。

- 主にファームウェア（あらかじめ機器の中に書き込まれている専用のソフトウェア）やブートローダ（PCが起動するときに一番最初に実行されるプログラム）を格納
- 電源を切っても消えない
- ROMに保存されている内容（プログラムやデータ）は、基本的にユーザーが変更することはない

### RAMとROMの違いを整理

RAMは、CPUがデータを読み書き（書き換え）しながら使うための部品です。</br>
プログラムを動かしたり、ファイルを開いたりするたびに、RAMの中身はどんどん書き換わります。</br>
一方、ROMは「基本的に内容を書き換えたり消したりできない」保存用の場所です。</br>
一般的に「メモリ」と言う場合は、RAM（作業用の一時的な記憶装置）を指します。</br>
ROMは特殊な用途のため、普段はあまり意識しなくても大丈夫です。

## ストレージ：データの倉庫

ストレージ（HDD/SSDなど）は、データを長期的に保存するための装置です。

### 特徴

- 電源を切ってもデータが消えない（不揮発性）
- OSやアプリケーション、ファイルなどを保管する場所
- CPUが実際に処理するためには、ストレージからデータをメモリに読み込む必要がある

### ストレージのタイプ

**HDD（ハードディスクドライブ）**
- 回転する磁性ディスクにデータを保存
- 容量が大きく、価格が安い
- ただし、機械的な動作のためアクセス速度は遅い

**SSD（ソリッドステートドライブ）**
- 電子回路でデータを保存（機械的な動作なし）
- HDDよりも圧倒的に速い
- 価格は高めだが、近年は安くなってきて主流になりつつある

### 倉庫の例え話

- **ストレージ = 倉庫**
  - 製品や材料（データ）を長期間保管する場所
  - 倉庫が遠いと、取りに行くのに時間がかかる（アクセス速度が遅い）
- **メモリ = 作業場**
  - 倉庫から持ってきた材料を使って、実際に作業をする場所
  - 作業場が広いほど効率的に仕事ができる

実際、CPUとメモリは物理的にも論理的にも「とても近い場所」にあります。CPUはすぐ隣のメモリからデータを高速にやり取りできます。

**まとめ**</br>
データはまずストレージ（倉庫）に保存され、必要なときにメモリ（作業場）に持ってきて処理されます。

## ネットワークインターフェース：外の世界とのつながり

サーバーは単体で動くだけでなく、他のサーバーやインターネットとデータをやり取りする必要があります。そこで必要になるのがネットワークインターフェースです。</br>
ネットワークインターフェースは、**サーバーが外の世界（他のサーバーやインターネット）とつながるための窓口**です。

### 役割

- サーバーがデータを送ったり受け取ったりするために使う「出入り口」
- ケーブルを差す場所（LANポート）や、ネットワークカード（NIC）がこれにあたる

### 通信速度

データの流れる速さ（電気や光）は一定です。</br>
そのため、通信速度は「1秒間にどれだけ多くのデータを送れるか」で決まります。</br>
「1秒間に送れるデータ量」をスループットといいます。

- 1Gbps（1ギガビット毎秒）：昔の基準
- 10Gbps：最近のデータセンター標準
- 100Gbps：超高速が必要な場合

**例え話**</br>
工場の「出荷口」のイメージ
- 工場で作った製品（データ）を外に出す場所
- 出荷口が狭い（1Gbps）と、トラック（データ）が渋滞して遅くなる
- 出荷口が広い（100Gbps）と、大量の荷物をスムーズに出せる

## バス：部品同士を結ぶ通路

ここまで、サーバーが外部とデータをやり取りする仕組みを説明しました。</br>
そして、サーバー内部での部品同士のデータのやり取りについては**バス**という通路が使われます。</br>
CPU、メモリ、ストレージ、ネットワークカードなどの部品は、バスを通じて情報を交換します。

### バスの種類

バスにはいくつか種類があります。主なものは次の2つです。

**システムバス**
- CPUとメモリをつなぐ
- データを高速に運ぶ必要があるため、非常に高速

**I/Oバス**
- CPUと周辺機器（ストレージ、ネットワークカード、USB機器など）をつなぐ
- 昔：PCI という規格
- 現在：PCI Express（PCIe）が主流

### 廊下の例え話

会社の廊下を想像してください。

- 廊下が狭いと、人（データ）がすれ違えずに渋滞する
- 廊下が広いと、たくさんの人が同時に通れる

バスもこれと同じで、バス幅（何ビットのデータを同時に運べるか）が広いほど、スループットが大きくなります。</br>
ネットワークインターフェースの「出入り口が広いほど速い」と同じです。

# Webシステムの実装を詳しく学ぶ

ここまで、基本的な考え方と物理的なハードウェアについて学びました。</br>
ここからは、実際にWebシステムがどのように構築され、運用されているのかを見ていきましょう。

## 3階層型システムの詳細な動作

3階層型システムについては既に簡単に説明しましたが、ここでもっと深く掘り下げていきます。

### Web層の役割

Web層は、**ユーザーのブラウザとAPサーバーの橋渡し役**です。

具体的には：
- HTTP/HTTPSリクエストを受け取る
- 適切なAPサーバーにリクエストを振り分ける（負荷分散）
- APサーバーからの応答をHTMLやJSON形式で整形
- ブラウザに返す

使われるソフトウェア：
- Nginx：軽量で高速
- Apache：昔からあるWebサーバー
- IIS（Internet Information Services）：Windows用

### AP層の役割

AP層は、**システムの頭脳**です。

具体的には：
- Web層からのリクエストを解析
- ビジネスロジック（複雑な計算や判断）を実行
- データベースに対してクエリを発行
- ビジネスルールに基づいて、返すデータを加工・変換
  - 一般会員には通常価格、プレミアム会員には割引価格を返す、など

使われるプログラミング言語：
- Java：大規模システムで人気
- Python：シンプルで学びやすい
- JavaScript：Node.jsという実行環境を使ってサーバーサイドで実行
- Go：モダンで高速

### DB層の役割

DB層は、**企業の重要な資産を管理する**層です。

具体的には：
- リレーショナルデータベース（RDBMS：表（テーブル）形式でデータを管理するデータベース）でデータを管理
- SQLクエリを実行して、データを検索・更新・削除
- トランザクション管理（例：銀行の振込処理など、複数の操作をまとめて失敗なく実行する仕組み）
- バックアップとリカバリ（万が一の障害や誤操作に備えて、データを守るための仕組み）

使われるデータベース：
- MySQL：シンプル、広く使われている（OSS版と商用版あり）
- MariaDB：MySQLから分岐したOSS
- PostgreSQL：高機能、拡張性が高い（OSS）
- Oracle Database：大企業向け、商用
- SQL Server：Windows系企業向け、商用
- NoSQL（MongoDB、DynamoDBなど）：大量データや多様なデータ形式、スケーラビリティが求められるケース
  - NoSQLは「ドキュメント型（JSONなど）」「キー・バリュー型」「グラフ型」など、様々なデータ構造をそのまま保存できる
  - つまり、RDBMSと違ってデータ構造がシンプル（データ同士の複雑な関係や結合が少ない）
  - そのため、データを「分割（シャーディング）」することができる（たくさんのサーバーで同時に処理できる）

## 負荷分散：複数のサーバーにアクセスを振り分ける

Xのトレンドが急に盛り上がったら、大量のアクセスが集中します。1台のサーバーでは対応できません。</br>
そこで登場するのが**負荷分散**です。

### ロードバランサー

負荷分散装置（ロードバランサー）は、**やってきたリクエストを複数のサーバーに振り分ける**装置です。

**例え話**</br>
テーマパークの入り口で、複数のゲートがあり、スタッフが「空いているゲートにどうぞ」と案内することで、混雑を防いでいるイメージです。

### 負荷分散のアルゴリズム

ロードバランサーは、いくつかの方法（アルゴリズム）を使い分けて、アクセスを効率よくサーバーに振り分けます。

- **ラウンドロビン**：サーバーA → B → C → A → B → … の順で振り分け（シンプルで均等だが、サーバーごとの負荷が違う場合は不向き）
- **最小接続数**：今つながっている接続数が最少のサーバーに振り分け（混雑していないサーバーを優先）
- **レスポンスタイム**：レスポンスが速いサーバーを優先（性能差がある場合に有効）
- **スティッキーセッション**：同じユーザーのアクセスを常に同じサーバーに振り分け（セッション管理やログイン状態の維持に便利）
  - IPハッシュ：ユーザーのIPアドレスをもとにサーバーを決定
  - Cookieベース：ユーザーのWebブラウザに保存されているCookie情報をもとにサーバーを決定

### ロードバランサー自体の冗長化

ここで1つ問題が出てきます。</br>
Q：ロードバランサーが壊れたらどうする？</br>
A：事前に**予備を用意**しておいて、その予備に変わりをさせます。</br>
予備を用意しておくことを**冗長化**といいます。

- プライマリ：通常時はこっちのロードバランサーが動く
- セカンダリ：プライマリが落ちたら自動的にこっちへ切り替わる

セカンダリへ自動で切り替わることを**フェイルオーバー**といいます。</br>
これを**ハートビート**という仕組みで実現します。</br>
プライマリが定期的に「私は元気です」という信号を送り続け、セカンダリがそれを受け取って監視します。</br>
そして信号が止まったら切り替える、というわけです。</br>
※逆に監視する側が「今どうなってる？」と定期的に相手に問い合わせる方式はポーリングといいます。

## 冗長化

ロードバランサーの冗長化を紹介しましたが、実際には他の重要な機器でも冗長化がよく行われます。

**Webサーバーの冗長化**
- 通常：サーバーAがメインで動く
- 障害時：サーバーBへ自動的に切り替わる
- または：AとBが並列で動き、ロードバランサーが振り分け

**データベースの冗長化**
- マスター・スレーブ構成：メインのDBに書き込み、別のDBに複製（書き込みは1台、読み取りは複数台で分散）
- または：複数のマスターが存在し、どこにでも書き込める（マルチマスター）

### 冗長化のコスト

冗長化するには2倍のサーバーが必要なので、2倍のコストがかかります。</br>
しかし、銀行などの重要なシステムでは、万が一の障害でもサービスを止めないために、冗長化は必須の投資とされています。</br>
冗長化によって、システムの「止まりにくさ（可用性）」を高めることができます。

**可用性の具体例**
- 99.9%：年間8.76時間ダウンしてもOK
- 99.99%：年間52.6分のダウンしてもOK
- 99.999%：年間5.26分のダウンしてもOK
- 99.9999%：年間31.5秒のダウンしてもOK

サービスの重要度によって、どれくらいの可用性を目指すかが決まります。

## 分散処理：大きな仕事を複数のサーバーで分担する

冗長化によってシステムの信頼性や可用性を高めることができますが、他の要件として、大量のデータや高い処理能力が求められる場面も多いです。</br>
そこで登場するのが**分散処理**です。分散処理とは、大きな仕事を複数のサーバーで手分けして行う方法です。

### 実例

- ログファイル分析：大量のアクセスログを集計して、よく見られているページを分析
- 画像処理：大量の写真を圧縮する処理

### MapReduceという考え方

分散処理を効率よく行うための代表的な仕組みとして、Googleが開発した**MapReduce**という考え方があります。

1. **Map フェーズ**：データを分割して、複数のサーバーに振る → 各サーバーが処理する
2. **Reduce フェーズ**：各サーバーの結果をまとめて、最終結果を作る

## 仮想化：1台の物理サーバーを複数に分割する

分散処理のようにたくさんのサーバーを使う場合、**サーバーを無駄なく使うことや必要に応じて簡単に増減できること**が重要です。</br>
そこで登場するのが**仮想化**という技術です。

### 仮想化の考え方

昔は、1台の物理サーバーに1つのOSと1つのアプリケーションしか載せられず、CPUやメモリを使い切れないまま新しいサーバーを追加することも多く、非効率でした。</br>
仮想化は、1台の物理サーバーの中に**複数の仮想サーバー（仮想マシン）**を作って動かす技術です。

**例え話**</br>
大きな部屋（物理サーバー）をパーテーションで区切って、小さなオフィス（仮想サーバー）をいくつも作るイメージ。

### メリット

- 物理サーバーを有効活用できる
- サーバーの追加・削除が柔軟（パーテーションを増やす/減らすだけ）
- バックアップや移行がやりやすい（仮想マシンごと丸ごとコピーして、他のサーバーに移動できる）
- 1台の物理サーバーを複数の用途で使えるので、台数を減らせる

### 仮想マシン（VM）

仮想マシンには大きく分けて「ハイパーバイザー型」と「ホスト型」があります。</br>
どちらも「1台の物理サーバーで複数の仮想マシンを動かす」ことができますが、用途や性能要件によって使い分けられます。

**ハイパーバイザー型（ベアメタル型）**
- 物理サーバーの上で直接ハイパーバイザーが動き、その上でVMが動作する
- サーバーを本格的に運用したい場合や、高いパフォーマンス・安定性が必要な場合に向いている
- VMware ESXi、KVM、Hyper-Vなど

```
【物理サーバー】
    ↓
【ハイパーバイザー】← 仮想化管理ソフト
    ↓
【VM1】【VM2】【VM3】
```

**ホスト型**
- 既存のOS（WindowsやLinuxなど）の上で仮想化ソフトを動かし、その上でVMが動作する
- 個人のPCや開発・テスト環境など、手軽に仮想マシンを使いたい場合に向いている
- VirtualBox、VMware Workstation、Parallels Desktopなど

```
【物理サーバー】
    ↓
【ホストOS（Windows/Linuxなど）】
    ↓
【仮想化ソフト（VirtualBoxなど）】
    ↓
【VM1】【VM2】
```

### コンテナ

最近では、さらに軽量で柔軟な**コンテナ**という新しい仮想化技術が流行っています。</br>
コンテナは、仮想マシンよりも少ないリソースで、アプリケーションごとに独立した実行環境をすばやく作れるのが特徴です。

**仮想マシン**
- OSが含まれていて、完全に独立した環境
- 重い、起動に時間がかかる

**コンテナ**
- OSカーネル（OSの中核部分）はホストと共有しつつ、ライブラリやツールなどのアプリケーション実行環境（ユーザーランド）だけを個別に持つ
- 無駄が少なくて軽量、起動が速い（秒単位）
- Dockerが有名

```
【物理サーバー】
    ↓
【ホストOSのLinuxカーネル】← 共有
    ↓
【コンテナ1】【コンテナ2】【コンテナ3】
```

コンテナは軽量がゆえに複製をしたりスケーリングしたりが簡単なので、クラウドネイティブ（クラウド環境の特性を最大限に活かす考え方）な設計で広く使われています。
